# ЛР3. Проектирование ленты подписок

## Цель

Спроектировать получение ленты пользователя - сообщений авторов, на которых он подписан. Сравнить способы формирования ленты и выбрать вариант с объяснением компромиссов.

## Исходная архитектура

Система разделена на сервисы:

- **Service Users** хранит пользователей, роли и подписки.
- **Service Messages** хранит сообщения и реакции, отдаёт общую ленту и ленту подписок.
- **Service Feed** в базовом варианте не нужен: его можно добавить, если измерения покажут, что получение ленты стало узким местом.

Каждый сервис работает со своей базой. Messages не читает таблицу подписок напрямую: список авторов он получает от Users по внутреннему API.

## Требования к ленте

1. Показывать сообщения авторов, на которых подписан текущий пользователь.
2. Сортировать от новых к старым.
3. Поддерживать постраничную выдачу без повторов и пропусков при появлении новых сообщений.
4. Пустой список подписок должен возвращать пустую ленту.
5. Авторство и подписчика определять по токену, а не принимать как доверенные значения от клиента.
6. Изменение подписки должно влиять на следующие запросы ленты.

## Варианты формирования ленты

### Вариант 1. Собирать при каждом чтении (fan-out on read)

При запросе ленты Messages узнаёт у Users список авторов, выбирает их сообщения из собственной базы, сортирует и возвращает страницу.

**Плюсы:** простая реализация; не нужно хранить копии ленты; публикация сообщения - одна запись; новое сообщение сразу попадает в ленту.

**Минусы:** каждый запрос зависит от Users; при большом числе подписок выборка и сортировка становятся дороже; одинаковые ленты пользователей пересчитываются.

### Вариант 2. Кэшировать ленту общего набора подписок

Пользователи с одинаковым набором авторов используют общий ключ набора (например, `set_id`) и общие закэшированные страницы. При чтении Messages запрашивает у Users набор и сначала проверяет кэш. При публикации автора инвалидируются кэши наборов, в которые он входит.

**Плюсы:** повторное чтение одинаковых лент быстрее; публикация не требует записи в ленту каждого подписчика - редкий случай, когда нужно запрашивать одну и ту же страницу ленты в течении короткого времени.

**Минусы:** одинаковые наборы подписок могут встречаться редко; нужно создавать и удалять наборы, поддерживать соответствия и инвалидировать кэш; при промахе всё равно выполняется обычная выборка.

### Вариант 3. Заранее собирать ленту каждого подписчика (fan-out on write)

При публикации сообщения Feed получает подписчиков автора и записывает ссылку на сообщение в ленту каждого из них. При чтении обычно достаточно выбрать готовые элементы ленты.

**Плюсы:** быстрое чтение; на запрос ленты не требуется собирать сообщения многих авторов.

**Минусы:** одна публикация может вызвать много записей; нужны очередь, повторная обработка и защита от дублей; подписка требует загрузить недавние сообщения автора, отписка - удалить их из ленты; популярный автор создаёт большую нагрузку. Для очень популярных авторов часто применяют гибрид: обычных авторов раскладывают при записи, а сообщения популярных авторов добавляют при чтении.

## Сравнение

| Критерий | 1. Сбор при чтении | 2. Общий кэш по набору | 3. Готовая лента пользователя |
|---|---|---|---|
| Скорость чтения | Средняя, зависит от числа авторов | Высокая при попадании в кэш | Высокая |
| Стоимость публикации | Низкая | Низкая, плюс инвалидирование | Может быть высокой |
| Дополнительное хранилище | Нет | Кэш страниц и наборы | Записи ленты для подписчиков |
| Сложность | Низкая | Средняя/высокая | Высокая |
| Актуальность | Сразу после записи сообщения | Зависит от инвалидирования/TTL | Зависит от доставки события |
| Подходит для | Небольшой/умеренной нагрузки | Повторяющихся наборов подписок | Большого числа чтений и контролируемой нагрузки записи |

## Выбор

Для проекта выбирается **вариант 1 - собирать страницу ленты при каждом запросе, без кэша**.

Причины:

- это самый простой вариант для текущего разделения Users и Messages;
- не нужны кэш, отдельный Feed Service, очередь событий или дополнительная таблица готовой ленты;
- сообщения и подписки остаются источниками истины, поэтому не нужно синхронизировать копии;
- новые сообщения и изменения подписок учитываются при следующем запросе.

Компромисс: каждый запрос зависит от Users, а рост числа подписок увеличивает работу Messages. Если измерения покажут, что лента стала узким местом, кэш можно добавить отдельно.

## Алгоритм выбранного варианта

1. Клиент вызывает Messages с access token и параметрами страницы.
2. Messages проверяет токен и получает `subscriber_id`.
3. Если у пользователя нет роли `subscriber`, сервис возвращает `403`.
4. Messages вызывает внутренний endpoint Users и получает `producer_ids`.
5. Если список пуст, Messages возвращает пустую страницу с `total: 0`.
6. Messages выбирает актуальные сообщения авторов, применяет cursor, сортирует результат и возвращает страницу. Кэш не используется.

### SQL-эскиз

```sql
SELECT id, author_id, text, created_at
FROM messages
WHERE author_id = ANY (:producer_ids)
  AND (created_at, id) < (:cursor_created_at, :cursor_id)
ORDER BY created_at DESC, id DESC
LIMIT :page_size_plus_one;
```

Для первой страницы условие по cursor не добавляется. `id` используется как дополнительный порядок при одинаковом `created_at`. В `messages` нужен индекс:

```sql
CREATE INDEX IF NOT EXISTS idx_messages_author_created_id
    ON messages (author_id, created_at DESC, id DESC);
```

## Пагинация

Используется cursor-пагинация, а не `OFFSET`. Cursor кодирует `created_at` и `id` последнего элемента страницы. Следующая страница выбирает строки, которые строго старше этой пары.

Это устойчивее при появлении новых сообщений между запросами: новые записи не сдвигают уже просмотренную страницу. Ответ содержит `next_cursor`; если следующей страницы нет, значение равно `null`. Размер страницы ограничивается, например, диапазоном 1-100.

## API-контракт ленты

### Получить ленту подписок

`GET /api/v1/messages/feed?limit=20&cursor=<opaque-cursor>`

Заголовок: `Authorization: Bearer <access-token>`.

Успешный ответ `200 OK`:

```json
{
  "items": [
    {
      "id": 42,
      "author_id": 7,
      "text": "Опубликовал новое сообщение",
      "created_at": "2026-11-26T10:00:00Z"
    }
  ],
  "next_cursor": "<opaque-cursor>"
}
```

Ошибки:

- `400 Bad Request` - некорректный cursor или `limit` вне диапазона.
- `401 Unauthorized` - токен отсутствует или недействителен.
- `403 Forbidden` - у пользователя нет роли `subscriber`.
- `503 Service Unavailable` - Users временно недоступен.

### Внутренний запрос к Users

`GET /internal/users/{userId}/subscriptions`

Пример ответа `200 OK`:

```json
{ "producer_ids": [7, 12, 18] }
```

Внутренний маршрут не публикуется для клиентских вызовов и защищается межсервисной авторизацией. При таймауте/ошибке Users Messages возвращает `503`, а не пустую ленту: пустой список означал бы, что подписок действительно нет.

## Изменения данных и согласованность

Готовая лента не хранится:

- новое сообщение появляется в ленте при следующем запросе;
- подписка или отписка меняет список авторов в Users и учитывается при следующем запросе;
- удалённое сообщение перестаёт попадать в выдачу из Messages.

Поскольку кэш и копии ленты не используются, отдельная инвалидация не нужна.

## Границы решения

В первой версии не добавляются отдельный Feed Service, очередь, материализованная лента или кэш. При каждом запросе Messages собирает актуальную страницу из сообщений авторов, на которых подписан пользователь. Перед переходом к более сложной схеме следует измерить задержку запроса, число подписок пользователя, число сообщений и частоту чтения/публикации.
